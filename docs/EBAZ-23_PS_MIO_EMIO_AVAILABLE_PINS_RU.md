# EBAZ-23 — какие физические контакты доступны из контроллеров PS Zynq

Дата: 2026-11-07. **Назначение:** технический справочник; продуктовые работы и образовательная документация существуют параллельно. Не путать возможности кристалла с доступными выводами конкретной платы и уже запущенными драйверами.

## Три различных уровня

1. **PS MIO (54 мультиплексируемых вывода)**: сигналы от контроллеров PS могут выходить непосредственно на шарики MIO, если трассированы на плате; не являются выводами PL. Функции MIO задаёт PS pinmux.
2. **PS EMIO**: отдельные сигналы от контроллеров PS маршрутизируются *через конфигурацию PL* на контакты FPGA; так можно получить аппаратные PS UART, SPI, I2C, GPIO, CAN и др. при соблюдении ограничений Zynq и FPGA XDC. Не каждый PS контроллер поддерживает EMIO; NAND/USB не становятся доступными таким образом.
3. **Пользовательская FPGA логика (PL)**: AXI UARTLite, GPIO, SPI, I2C, PWM, video и прочие IP, реализованные в Vivado, и напрямую работающие с FPGA I/O. Это **не тот же самый** аппаратный PS контроллер.

## Разъёмы конкретной EBAZ4205

- По [darktjm/ebaz.xdc](https://github.com/darktjm/ebaz/blob/master/ebaz.xdc) доступны три DATA-разъёма по 20 позиций, в XDC описано по **14 цифровых сигналов PL** на DATA1, DATA2, DATA3; не считать все 60 позиций FPGA GPIO.
- [Справочная полная CSV-таблица 42 сигналов](../hardware/EBAZ4205_DATA_CONNECTORS_PINMAP.csv). Поправлено расхождение: для шарика FPGA G20 на DATA2 в [xjtuecho pinout](https://github-wiki-see.page/m/xjtuecho/EBAZ4205/wiki/Pinouts) указан **DATA2 pin 5** (у некоторых сторонних XDC записан pin 4), поэтому физическую нумерацию разъёма проверять до разводки кабеля.
- Сильно занятые PL выводы PHY Ethernet **не свободные**: RX U14/Y16/V16/V17/Y17/W16, TX U15/W18/Y18/V18/Y19/W19, MDIO W15/Y14, возможный PHY 25 MHz U18. Остальные аппаратные LED/FAN — не автоматически доступные GPIO: [darktjm XDC](https://github.com/darktjm/ebaz/blob/master/ebaz.xdc).
- Из иных авторских примеров PL UART H16/H17, LCD T20/R18/N17/R19/P20, кнопки T19/P19/U20/U19/V20, LED E19/K17/H18. Эти назначения *только в соответствующем стороннем FPGA проекте*, не в текущем stock bitstream.
- Напряжение внешнего разъёма/банка, назначение контактов питания и ориентацию разъёма определять только по электрической схеме и конкретному физическому экземпляру перед подключением.

## Контроллеры и доступность — два независимых признака

| Контроллер | Внутри Zynq | Обнаружен нашим Linux | Подключение наружу |
|---|---|---|---|
| PS GPIO | Да, MIO+EMIO | PS GPIO controller at 0xe000a000 (iomem) | На MIO только при проводке платы; EMIO только при FPGA pinmux |
| PS UART | Два | ttyPS0 115200, ttyPS1, PS UART resources e0000000, e0001000 | ttyPS0 физически соединён с UART-консолью; ttyPS1 физическое место не проверено |
| PS I2C | Два | e0004000 в iomem | Нет подтверждения о конкретном свободном разъёме; возможен MIO/EMIO по проекту |
| PS SPI | Два | e0007000 в iomem | Нет подтверждения о конкретном свободном разъёме; возможен MIO/EMIO по проекту |
| PS SDIO | Два | e0100000 (mmc0) | Установленность SD-сокета на экземпляре неизвестна; SDIO через MIO, не универсальный EMIO |
| PS Ethernet GEM | Два | e000b000, работающий eth0 | PHY через Ethernet EMIO/PL, RJ45; необходимые выводы заняты |
| PS CAN | Два | Драйвер и разъём на нашем Linux не подтверждены | В принципе возможен через MIO/EMIO при нужной конфигурации; отсутствие физического CAN трансивера на базовой плате учитывать |
| PL UARTLite | В *FPGA IP*, не PS | ttyUL2, MMIO 0x42c00000, обмен ранее подтверждён | Текущая физическая маршрутизация на DATA-разъёмы не доказана |
| PL AXI BRAM | В *FPGA IP* | MMIO 0x40000000, 128 bytes READ PASS | Не внешний контакт: аппаратная память, не GPIO |

Наличие ресурса по `/proc/iomem` — не свидетельство наличия выведенных на наружный разъём проводников. И наоборот, известный PL ball pin в XDC других авторов — не гарантия активности в штатном bitstream.

## Как установить **для нашей текущей прошивки**, без изменения NAND/FPGA

Выполнить read-only shell:

```sh
echo '=== PS CONTROLLERS ==='
ls /sys/bus/platform/devices | grep -E 'e0000000|e0001000|e0004000|e0005000|e0006000|e0007000|e0008000|e000b000|e0100000|e0101000|e000a000'
echo '=== GPIOCHIP ==='
for d in /sys/class/gpio/gpiochip*; do [ -d "$d" ] || continue; echo "$d"; cat "$d/base" "$d/ngpio" "$d/label" 2>/dev/null; done
echo '=== PLATFORM DEVICES ==='
ls /sys/bus/platform/devices
echo '=== PL INTERFACES ==='
ls /sys/firmware/devicetree/base/amba_pl
echo '=== PS PINMUX DRIVERS ==='
ls /sys/kernel/debug/pinctrl 2>/dev/null || true
```

Сами показания sysfs не доказывают, какие MIO разведены наружу: следующая стадия — фото двух сторон платы, ревизия, сравнение PCB/схемы и безопасная прозвонка *без питания*.

## Инженерная и коммерческая логика

- Продавать как **42 PL сигнальных линии через 3 DATA разъёма (согласно опубликованной карте, требуется проверка ревизии)** плюс UART/Ethernet/Linux; не обещать «42 свободных PS GPIO» или «встроенные HDMI/I2C/SPI/CAN разъёмы».
- Дополнительный пакет обучения PS MIO/EMIO/PL и I/O mux — самостоятельная документационная работа, никак не отменяемая коммерческим планом.
- Если исходный проект открыт под подходящей лицензией, изучить и адаптировать с атрибуцией; если не разрешён, делать свою независимую реализацию той же функциональности, не копируя защищённый код. Ссылки на чужие проекты не означают, что функции предустановлены.

## Дополнение: конкретная трассировка PS MIO по опубликованной таблице mwalle

Источник: https://gist.github.com/mwalle/d8291e241075d82d1d420afa9302bd91 (таблица By pin -> MIO). Перенесена справочная карта **всех 54 шариков MIO**: [EBAZ4205_PS_MIO_PINMAP.csv](../hardware/EBAZ4205_PS_MIO_PINMAP.csv). Статус только REFERENCE; для нашей ревизии подключение кнопок/RTC/SD не проверено.

| MIO | Соединение на опубликованной PCB | Практический вывод |
|---|---|---|
| 0, 2–14 | NAND | ЗАНЯТЫ штатной загрузочной памятью, не использовать как GPIO |
| 24,25 | UART TX/RX | Штатная консоль, нельзя переназначать без запасного доступа |
| 20,32 | SW2, SW3 | **Кандидаты для теста входов GPIO** через sysfs, если это именно физические кнопки нашего экземпляра |
| 26,27 | RTC SCL/SDA | Возможный путь к I²C или GPIO, но зависит от RTC/обвязки и текущего mux |
| 34, 40–45 | SD_CD#, SD_CLK/CMD/DAT0–3 | Линии SDIO, физическое наличие слота/пайки проверить |
| 16,18 | PL_PS_CLK2 (?) / PL_PS_CLK1 (?) | Подключения к PL на PCB предполагаются, вопросительная пометка автора; не объявлять свободными |
| 28–31, 35, 38–39, 46–50 | boot strapping/pull-up | Не трогать: могут влиять на режим загрузки |
| 1,15,17,19,21–23,33,36–37,51–53 | NC по чужой карте | NC означает, что на данной разводке нет штатного соединения; **не означает доступный внешний разъём** |

Номера GPIO в **нашей работающей Linux с gpiochip base 906**: MIO20 = 926, MIO32 = 938, MIO26 = 932, MIO27 = 933. Не выставлять направление output и не экспортировать выводы загрузки/NAND без отдельного анализа. Наоборот, **сначала** читать `/sys/kernel/debug/gpio` (если debugfs смонтирован), `/sys/class/gpio/gpiochip906` и `/proc/device-tree` без записи.

Для Ethernet через PL: штатная Ethernet PHY работает, критические PL I/O заняты. Реальные свободные сигналы DATA (42 по чужой XDC) пока надо считать **аппаратно доступными по схеме, но не гарантированно свободными в текущем bitstream**.

## 2026-11-07 — сверка с ПЕРВОИСТОЧНИКАМИ (после подтверждения пользователем наличия кнопок и держателя SD)

**Новый первичный источник:** [mainline Linux Device Tree for EBAZ4205](https://github.com/torvalds/linux/blob/master/arch/arm/boot/dts/xilinx/zynq-ebaz4205.dts) — явные `gpio0_20_grp` и `gpio0_32_grp` (оба для PS GPIO), `sdio0_2_grp`, `gpio0_34_grp` для card detect, `&sdhci0 status = "okay"`. Это описание для Linux mainline, **не обязательно точный DTB заводского Linux 4.6**. В mainline DTS нет обязательного `gpio-keys`-устройства; настройки pinmux сами по себе не означают появление событий в `/dev/input`.

**Кнопки:** [mwalle pinout](https://gist.github.com/mwalle/d8291e241075d82d1d420afa9302bd91) определяет SW2 = PS MIO20 (A17), SW3 = PS MIO32 (A14); наш gpiochip `base=906`, поэтому Linux GPIO 926/938 (пока НЕ проверены непосредственно в пользовательском вводе). [KeitetsuWorks GPIO demo](https://github.com/KeitetsuWorks/EBAZ4205/blob/master/linux/ebaz4205/project-spec/meta-user/recipes-apps/gpio-demo/README.md) **реально демонстрирует** работающую пару S2/S3 в их PetaLinux: S2 замедляет мигание зелёного LED6G, S3 ускоряет, через `leds-gpio` и `gpio-keys` и исполняемый `gpio-demo`. Их код распространяется под MIT (см. LICENSE), потенциально можно заимствовать с атрибуцией и адаптацией под наше ядро 4.6.

**Возможное ограничение комплектации:** [Hardware Build States wiki](https://github-wiki-see.page/m/xjtuecho/EBAZ4205/wiki/Hardware-Build-States.-What-you-may-or-not-have-fitted-on-your-board.) говорит о возможном отсутствии обвязки S3 (`R2649`); KeitetsuWorks пишет о необходимости S3, `C2410`, `R2641A` в их ревизии. Эти номера не объединять в одну безусловную инструкцию. Наш пользователь подтвердил физическое наличие двух кнопок; электрическую связь ещё предстоит проверить.

**microSD:** [mwalle](https://gist.github.com/mwalle/d8291e241075d82d1d420afa9302bd91) фиксирует PS MIO40=CLK, 41=CMD, 42..45=DAT[0..3], 34=CD#. Наш Linux имеет `e0100000.sdhci`. Пользователь сообщает о физическом держателе SD. **Работа SD в NAND-boot пока не проверена**; проверить `/sys/class/mmc_host`, `/dev/mmcblk*`, dmesg без модификаций. Для самостоятельной загрузки с SD [xjtuecho](https://github.com/xjtuecho/EBAZ4205) указывает перенести boot-strap резистор с R2584 (NAND) на R2577 (SD); [KeitetsuWorks](https://github.com/KeitetsuWorks/EBAZ4205) требует R2577 и U7. Ничего не перепаивать до резервной копии и плана повторяемости товарной партии.

**DDR3:** [xjtuecho README](https://github.com/xjtuecho/EBAZ4205) и [reconstructed KiCad Mem_Zynq](https://github.com/xjtuecho/EBAZ4205/blob/master/HW/ebaz4205/kicad/Mem_Zynq.kicad_sch) указывают одну внешнюю DDR3/DDR3L IC, эталонный компонент Micron MT41K128M16JT-125 и 256 MB. Контроллер DDR является блоком **PS**, а сама оперативная память физически расположена **в отдельной микросхеме** вне кристалла Zynq, подключённой специальной DDR-шиной (не MIO GPIO). Код Linux управляет RAM через PS DDR controller; PL может адресовать DDR посредством AXI PS↔PL при соответствующем дизайне. Конкретную маркировку микросхемы на нашем экземпляре ещё не снимали. Наш `MemTotal=252032 kB` согласуется с номинальным 256 МиБ (часть RAM зарезервирована для ядра/оборудования).

**Коммерческая ценность**: готовая демо-пара «две кнопки меняют мигание LED» уже реализована под EBAZ4205, не нужна новая FPGA RTL; демонстрация чтения microSD под **штатной NAND-системой** потенциально особенно выгодна без перепайки загрузочных резисторов. Не обещать обе функции в карточке продажи, пока на нашем экземпляре не отмечены тесты PASS.

Только-чтение для следующего шага (никакого `gpio export` и изменений pinmux):
```sh
echo '=== INPUT DEVICES ==='
cat /proc/bus/input/devices
echo '=== MMC HOST ==='
ls -l /sys/class/mmc_host/ 2>/dev/null
echo '=== DETECTED MEDIA ==='
ls -l /dev/mmcblk* 2>/dev/null
echo '=== SD LOG ==='
dmesg | grep -i -E 'mmc|sdhci|card detect'
echo '=== GPIO DEBUG ==='
cat /sys/kernel/debug/gpio 2>/dev/null
```

## 2026-11-07 — пользовательские красный/зелёный LED: фотографии и XDC

**SW2/SW3 INPUT PASS:** пользователь нажимал реальные кнопки в `/tmp/ebaz23-gpio-buttons`; терминал показал четыре `Нажата кнопка SW3` и три `Нажата кнопка SW2`. Это подтверждает работу **именно кнопок**, не LED.

**Расположение LED на плате:** два маленьких пользовательских LED расположены **между блоком кнопок и разъёмом RJ45**, вдоль края платы. Маркированное фото: [tonyho — board front with labels](https://github.com/tonyho/EBAZ4205-Minimum-Board-Operating-Configuration/blob/master/Documents/ebaz4205.jpg); независимая фотография той же стороны: [xjtuecho — PCB top layer](https://github.com/xjtuecho/EBAZ4205/blob/master/image/01-PCB-TL.jpg). Не путать с индикаторами Ethernet PHY, POWER и DONE.

**Физическая карта PL подтверждается двумя XDC:**
- [xjtuecho/Development/EBAZ4205.xdc](https://github.com/xjtuecho/EBAZ4205/blob/master/Development/EBAZ4205.xdc): greenLED = **W13**, redLED = **W14**;
- [darktjm/ebaz.xdc](https://github.com/darktjm/ebaz/blob/master/ebaz.xdc): LED_GREEN = **W13**, LED_RED = **W14**, и комментарий автора *"Apparently emio[0] is red, and emio[1] is green by default"*; это заявление об observed mapping автора, не гарантия трассировки в нашем factory bitstream;
- [KeitetsuWorks device tree](https://github.com/KeitetsuWorks/EBAZ4205/blob/master/linux/ebaz4205/project-spec/meta-user/recipes-bsp/device-tree/files/ebaz4205.dtsi) задаёт GPIO54(EMIO0) = red, GPIO55(EMIO1) = green, ACTIVE_LOW, при **их собственной** FPGA-конфигурации.

**Важный вывод:** GPIO960/961 в нашем Linux соответствуют EMIO0/1 на стороне PS, но связи EMIO0→W14 и EMIO1→W13 **на установленном штатном bitstream пока не подтверждены**. Запись в эти GPIO сейчас не является безопасно предсказуемым тестом светодиодов: возможны другие соединения. Не включать контроль LED в коммерческие PASS до реального эксперимента.

Факт по нескольким источникам: светодиоды найдены на фотографиях и у нас есть физические FPGA ball-пины W13/W14. Для дальнейшей проверки — сначала read-only анализ текущей карты `/sys/class/leds`, DT и разрешённых GPIO. 

## 2026-11-07 — новая информация о заводских LED и диагностике без записи

**Прямая информация владельца нашей платы:** в исходной майнинговой прошивке при потере доступа к Интернету происходило переключение индикации **зелёный → красный**. Это сильное свидетельство, что аппаратный маршрут и логика управления парой LED **существовали в исходной комбинации software + factory bitstream**; но оно само по себе не доказывает, проверялось ли наличие именно Интернета, наличие Ethernet link или соединение с майнинговым пулом, и какой регистр/процесс использовался.

**Факты из очищенной системы:** `/sys/class/leds/` содержит **только `mmc0::`** (классный индикатор/триггер MMC, не подтверждённый физический зелёный или красный LED). Нет `led-red` или `led-green` и в `/firmware/devicetree/base/amba_pl` по-прежнему только UARTLite и AXI BRAM. Отсутствие в LED class не означает отсутствия подключения W13/W14.

**Общеизвестное описание исходного майнингового режима:** [EBAZ4205-Instruction](https://www.scribd.com/document/1071177324/EBAZ4205-Instruction) описывает LED6 как красный/зелёный индикаторы W13/W14; на заводском NAND-boot после подачи питания загорается зелёный, а приблизительно спустя минуту мигает красный (автор относит к запуску ПО майнера). Это наблюдение не следует приравнивать к точно определённому network-online индикатору. Независимые XDC подтверждают физические W13/W14.

**Следующее измерение только чтением**, по [AMD/Xilinx UG585](https://docs.amd.com/r/en-US/ug585-zynq-7000-SoC-TRM/GPIO-Control-of-Device-Pins) и [Linux gpio-zynq.c](https://github.com/torvalds/linux/blob/master/drivers/gpio/gpio-zynq.c):

```sh
echo '=== EMIO BANK2 GPIO OUTPUT DIRECTION ==='
/sbin/devmem 0xE000A284 32
echo '=== EMIO BANK2 OUTPUT ENABLE ==='
/sbin/devmem 0xE000A288 32
echo '=== EMIO BANK2 DATA LATCH ==='
/sbin/devmem 0xE000A048 32
echo '=== EMIO BANK2 PIN READBACK ==='
/sbin/devmem 0xE000A068 32
```

Для банка 2: **bit0=EMIO0 = Linux GPIO 960**, **bit1=EMIO1 = GPIO 961**. Если два младших бита **DIRM** и **OEN** установлены, PS выдаёт эти EMIO как выходы. Если сброшены — PS их не драйвит как GPIO-выходы в момент измерения. **Никакого теста переключения LED, записи в devmem или смены GPIO direction до анализа результатов.** Ethernet PHY подключён через PL, поэтому без установления реального маршрута GPIO может повлиять на сеть.

Следующая цель — выяснить, можно ли восстановить штатное программное управление LED, не перезаписывая работающий заводской bitstream и не вмешиваясь в NAND. Статус `LED_GREEN_RED_CONTROL_UNKNOWN`, а не FAIL.


## 2026-11-07 — фактическое чтение GPIO банка 2 на нашем экземпляре

Пользователь выполнил **только чтение** MMIO через BusyBox devmem на штатном Linux 4.6:
- `0xE000A284` **DIRM_2** = `0x00000000`;
- `0xE000A288` **OEN_2** = `0x00000000`;
- `0xE000A048` **DATA_2** = `0x00000000`;
- `0xE000A068` **DATA_2_RO** = `0x00000000`.

Интерпретация по [AMD UG585, GPIO Control of Device Pins](https://docs.amd.com/r/en-US/ug585-zynq-7000-SoC-TRM/GPIO-Control-of-Device-Pins): в момент теста PS GPIO EMIO банка 2 (EMIO0..31, Linux GPIO960..991) **не включены как GPIO-выходы**; регистр DATA =0 и читаемые значения =0. Эти данные не позволяют исключить наличие физического PL-пути к LED W13/W14, другого AXI-периферийного регистра или управления из PL без PS GPIO.

Прямое наблюдение пользователя о прошлой майнинговой прошивке: переключение зелёного/красного при потере Интернета. *Альтернативная интерпретация сообщества*: [EBAZ4205 Original LED startup description](https://theokelo.co.ke/getting-started-with-ebaz4205-zynq-7000/) сообщает, что красный и зелёный могут чередоваться при невозможности связаться с майнинговым сервером; [другое руководство](https://www.scribd.com/document/1071177324/EBAZ4205-Instruction) говорит, что зелёный горит сразу после подачи питания, красный начинает мигать приблизительно через минуту. Нужно экспериментально отделить состояние Ethernet-link, доступа к Интернету и пулу от факта запуска mining process.

**Решение по безопасности:** категорически не менять *целый банк GPIO* прямой записью `devmem` (может нарушить сетевые функции). Если требуется проверка физического LED, возможен только контролируемый тест **одного** отдельного GPIO (кандидат 960 — RED), через kernel GPIO sysfs, в локальной UART-консоли с автоматическим возвратом в input. Если направление другого выхода уже выставлено или GPIO занят драйвером, тест не проводить. Тест пока не выполнен; никаких LED PASS не объявлять.
