# EBAZ-16 — Диагностика CRC узла JFFS2 в NAND EBAZ4205

**Дата:** 2026-11-04  
**Статус:** повреждение данных одного raw-узла **подтверждено**, имя файла установлено; физический дефект NAND **не подтверждён**. Исследование выполнено без записи в NAND.

## Исходное сообщение ядра

```text
jffs2: notice: (721) check_node_data: wrong data CRC in data node at 0x019db640: read 0xcb068503, calculated 0x306c4195.
```

Сообщение повторяется при запуске. В загрузочном журнале также наблюдалось:

```text
jffs2: Empty flash at 0x019dc684 ends at 0x019dc800
```

Границы совпадают с длиной проблемного узла: `0x019DB640 + 0x1044 = 0x019DC684`. Промежуток до `0x019DC800` равен 380 байтам. Само сообщение `Empty flash` не является доказательством физического bad block.

## Адрес и геометрия

- Раздел: `mtd6` / `nand-allrootfs`, 64 MiB, смещение от начала всей NAND `0x02A20000`.
- Логический адрес узла в разделе: `0x019DB640`.
- Блок стирания: 128 KiB, индекс **206** (от нуля), начало в разделе `0x019C0000`.
- NAND: Winbond W29N01HV, 128 MiB SLC, страница 2048, OOB 64.
- На старте ядро читает BBT и сообщает четыре bad blocks в конце NAND `0x07F60000`, `0x07F80000`, `0x07FA0000`, `0x07FC0000`; они **в другом разделе** (`nand-reserve`) и не локализованы по адресу исследуемого узла.

## Неразрушающее чтение блока

Команда на плате:

```sh
/usr/sbin/nanddump -q --bb=padbad -s 0x019C0000 -l 0x20000 -f /run/mtd6_block206.bin /dev/mtd6
```

Код `0`, размер `131072` байта, SHA-256:

```text
287020d4dbc0ecbc835d6dc065cdcd08747b91232665c407919e3abd66ca7f48
```

Счётчики раздела `/sys/class/mtd/mtd6` после чтения:

```text
erasesize: 131072
bad_blocks: 0
bbt_blocks: 0
corrected_bits: 0
ecc_failures: 0
```

Это отсутствие **зарегистрированных** ошибок в измеренном состоянии, а не проверка ресурса NAND.

## Расшифровка JFFS2 и имя файла

Головка по смещению `0x019DB640` имеет JFFS2 magic `0x1985` и тип `raw_inode` (`0xE002`). Сканер, опубликованный в [tools/ebaz_jffs2_find_inode.py](../tools/ebaz_jffs2_find_inode.py), проверил данные в предварительно сохранённом 64-MiB образе `mtd6_allrootfs.bin`:

```text
inode=981 version=108893 mode=0100644 file_size=4725290
totlen=4164 fragment_file_offset=0x154000
stored_size=4096 unpacked_size=4096 compression=0
header_crc: stored=0x84D1586D actual=0x84D1586D PASS
node_crc:   stored=0x1C25EFB8 actual=0x1C25EFB8 PASS
data_crc:   stored=0xCB068503 actual=0x306C4195 FAIL
Valid raw dirents: 932
Dirents pointing to inode 981: 1
parent=401 version=795 name='btc_upgrade.tar.gz'
candidate path: /opt/work1/btc_upgrade.tar.gz
```

Таким образом, ошибка CRC **содержимого** 4096-байтного фрагмента доказана независимо от ядра. Фрагмент относится к архиву обновления майнингового ПО.

Текущая ОС подтвердила существование того же файла:

```sh
ls -ldi /opt/work1 /opt/work1/btc_upgrade.tar.gz 2>&1
```

```text
401 drwxr-xr-x ... /opt/work1
981 -rw-r--r-- ... 4725290 ... /opt/work1/btc_upgrade.tar.gz
```

```sh
gzip -t /opt/work1/btc_upgrade.tar.gz; echo "gzip_exit=$?"
```

```text
gzip_exit=0
```

## Ключевой контрольный эксперимент: файл против raw NAND

Сравнивались **одни и те же 4096 байт по логическому смещению 0x154000**. Фрагмент данных внутри raw-узла начинается через 68 байт после заголовка; в 128-KiB дампе блока это `0x1B640 + 68 = 112260`.

```sh
dd if=/opt/work1/btc_upgrade.tar.gz bs=4096 skip=340 count=1 2>/dev/null | sha256sum
# 1a22af6c90c3eeeac3f0109c077a92a48fb2c5c5388c8f647da3ef686ba73dff

dd if=/run/mtd6_block206.bin bs=1 skip=112260 count=4096 2>/dev/null | sha256sum
# 14336cd3fda2806ff4eb63e18f3a1ba37430f0eb012369387ab19834c06e2beb
```

**Факт:** текущий Linux возвращает для файла данные, отличающиеся от физического фрагмента с неправильной CRC. При этом gzip-поток успешно проходит `gzip -t`. Значит, повреждённый raw-узел **не является источником тех байтов, которые возвращаются при текущем чтении данного диапазона файла**.

**Наиболее вероятная интерпретация:** JFFS2 использует другую версию/копию фрагмента и не принимает проблемный raw-узел как актуальный. Для строгого доказательства механизма нужно отдельно просканировать все raw_inode версии inode 981, перекрывающие диапазон `0x154000...0x155000`, и сопоставить их данные, версии и CRC. Этого дополнительного исследования пока не делали.

## Решение

- **Не объявлять физический блок №206 неисправным** на основании лишь JFFS2 data-CRC; ECC в проверке не сигнализировал ошибки.
- **Не выполнять** `nandmarkbad`, `flash_erase`, `nandtest` в разрушающем режиме или перезапись NAND.
- **Не удалять** `/opt/work1/btc_upgrade.tar.gz` ради удаления сообщения; файл читается и успешно проходит `gzip -t`.
- Для EBAZ-15 (клиентской учебно-экспериментальной платы) вести неразрушающий контроль и отдельно документировать известные CRC-сообщения; не заявлять, что физический ресурс NAND проверен.
- Штатная загрузка Linux, DHCP, SSH, отсутствие майнера и холодный старт уже проверены в [EBAZ-14](EBAZ-14_AUTONOMOUS_LINUX_BOOT_RU.md).

**Итог:** локализован единственный зафиксированный дефект данных raw-узла JFFS2, относящегося к `/opt/work1/btc_upgrade.tar.gz`; физический дефект NAND по имеющимся данным не установлен. Стирать или переназначать блок не требуется.
