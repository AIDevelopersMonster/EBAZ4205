# AXI в Xilinx Zynq-7000: от программы ARM до памяти FPGA

**Практическая статья по результатам лаборатории EBAZ-20 (6 ноября 2026 г.)**

**Плата:** EBAZ4205, Zynq XC7Z010, два ARM Cortex-A9.  
**Linux:** PetaLinux 2016.4, ядро `4.6.0-xilinx`.  
**Эксперимент:** собственная программа ARM под Linux читает 128 байт через AXI по адресу `0x40000000`.  
**Видео:** [ARM читает FPGA — EBAZ-20, YouTube Shorts](https://youtube.com/shorts/LdDsGtTQiSQ).  
**Исходный код:** [software/ebaz20-bram-reader](../software/ebaz20-bram-reader/README.md).

> **Предмет доказательства:** работающая программа ARM успешно выполнила 32 последовательных чтения 32-битных слов через `/dev/mem` / `mmap()` в адресном диапазоне, соответствующем AXI BRAM Controller в Device Tree. Мы **не** доказали запись ARM в BRAM, отдельное чтение данных логикой PL, взаимное подтверждение сообщений, работоспособность всех 8 КиБ или то, что FPGA исполняет нашу новую RTL-программу.

## 1. Зачем процессору AXI

Zynq-7000 объединяет две подсистемы:

- **PS (Processing System)** — процессоры ARM Cortex-A9, память, контроллеры и программное обеспечение;
- **PL (Programmable Logic)** — аппаратные схемы, реализованные в программируемой логике FPGA.

У PS и PL нет необходимости обмениваться данными через UART или Ethernet. Между ними могут быть настроены встроенные интерфейсы **AXI** — семейство шинных протоколов **Arm AMBA AXI**, которыми связывают инициаторов транзакций (masters) и обслуживающие устройства (slaves).

Для процессора аппаратный блок в FPGA может выглядеть как область физических адресов. Выполнение обычной инструкции чтения ARM порождает транзакцию в системе памяти; межсоединение направляет её к соответствующему AXI-устройству PL. Оно отвечает данными, после чего инструкция завершается.

**Важная оговорка:** адрес `0x40000000` — это не универсальный «адрес FPGA». Он относится к конкретному описанию аппаратной системы, загруженной в нашу EBAZ4205. В другом bitstream адрес и размер могут отличаться.

### Три уровня, которые нельзя смешивать

| Уровень | Что происходит | Что это не означает |
|---|---|---|
| Приложение Linux | `open("/dev/mem")`, `mmap()`, `volatile` чтение слова | Не является AXI-командой в исходном коде C |
| Память/межсоединение Zynq | Обращение CPU преобразуется в адресную транзакцию к PL | Не обязательно использует отдельную DDR-память |
| Аппаратный IP в PL | AXI BRAM Controller принимает адрес и возвращает значение из связанной памяти | Не означает, что мы изменили RTL или доказали запись |

### Схематический тракт нашего чтения

```text
Приложение ebaz20-bram-reader (C, Linux userspace)
                    |
                    | open("/dev/mem", O_RDONLY)
                    | mmap(..., PROT_READ, MAP_SHARED, 0x40000000)
                    v
             ARM Cortex-A9 / MMU
                    |
             PS interconnect
                    |
        PS master AXI interface to PL
                    |
             AXI interconnect
                    |
         AXI BRAM Controller (PL)
                    |
              memory interface
                    |
             BRAM storage (PL)
```

Показана **функциональная**, не восстановленная по заводскому bitstream точная схема: конкретные промежуточные IP и порты AXI должны быть проверены по Vivado/block design или извлечённым аппаратным данным.

## 2. Что такое AXI: семейство, а не одна шина

**AXI4** — протокол адресно-ориентированных транзакций чтения/записи с возможностью пакетных (burst) обращений. **AXI4-Lite** — упрощённый вариант без burst, обычно применяемый для небольших регистров управления и состояния. **AXI4-Stream** передаёт поток данных без адреса памяти в каждой транзакции; он полезен, например, для видеоданных, DSP и непрерывного потока образцов.

| Интерфейс | Типичный объект | Характеристика |
|---|---|---|
| AXI4 memory-mapped | BRAM, память, DMA | Адресованные транзакции, burst-передачи |
| AXI4-Lite memory-mapped | Регистры IP: control/status/config | Простые одиночные передачи |
| AXI4-Stream | Видеопоток, DSP, пакеты | Данные без memory-mapped адреса каждой передачи |

Отдельно существует **AXI3** — более ранний протокол из семейства AMBA. Для старых систем Zynq-7000 важно не приписывать автоматически всем PS-портам свойства AXI4. Для каждого интерфейса требуется смотреть TRM и конфигурацию конкретного IP. Наличие в системе AXI BRAM Controller не доказывает использование именно AXI4-Lite.

## 3. Как организована транзакция AXI memory-mapped

Для AXI4/AXI4-Lite концептуально выделяют пять независимых каналов:

1. **AW (Write Address)** — адрес записи;
2. **W (Write Data)** — данные записи;
3. **B (Write Response)** — результат записи;
4. **AR (Read Address)** — адрес чтения;
5. **R (Read Data)** — данные чтения и ответ.

Передача по каналу осуществляется при одновременном утверждении `VALID` отправителем и `READY` получателем. Каналы допускают независимую задержку, поэтому адрес и данные не обязаны передаваться в один такт.

Для нашего опыта чтения принципиальна пара **AR + R**:

```text
PS / initiator                  PL / AXI BRAM Controller
       |                                     |
       |-- ARADDR=0x40000000, ARVALID ----->|
       |<---------------------------- ARREADY|
       |                                     |
       |<------- RDATA=0x00000043, RVALID --|
       |-- RREADY ------------------------->|
       |                                     |
```

Это **упрощённая логическая иллюстрация**, не осциллограмма и не замер реальных сигналов в PL. Реальные сигналы и число тактов в нашем эксперименте не измерялись. Также фактическая AXI-транзакция может возникать после промежуточной обработки адреса PS и interconnect.

### Адреса, размер и выравнивание

При 32-битном слове следующие последовательные адреса отличаются на 4 байта:

```text
0x40000000 — слово 0
0x40000004 — слово 1
0x40000008 — слово 2
0x4000000C — слово 3
...
0x4000007C — слово 31
```

`32 × 4 = 128 байт`. Это количество **проверенных байтов адресного окна**, а не доказательство полного размера аппаратной BRAM.

## 4. Что именно обнаружено на EBAZ4205

Из текущего Linux Device Tree:

```text
/proc/device-tree/amba_pl/axi_bram_ctrl@40000000
```

Поля:

| Параметр | Фактическое значение | Значение для эксперимента |
|---|---|---|
| `reg` | База `0x40000000`, длина `0x2000` | Описанное физическое окно 8 КиБ |
| `compatible` | `xlnx,axi-bram-ctrl-4.0` | IP AXI BRAM Controller |
| `xlnx,memory-depth` | 2048 | Параметр глубины памяти IP |
| `xlnx,bram-addr-width` | 11 | Параметр адресации BRAM |
| `xlnx,s-axi-ctrl-data-width` | 32 | 32-битный интерфейс данных |
| `xlnx,ecc` | 0 | ECC отключён в описании |
| `xlnx,single-port-bram` | 1 | Однопортовая конфигурация BRAM IP |
| `xlnx,bram-inst-mode` | `EXTERNAL` | Модуль памяти реализован отдельно от контроллера IP |

Важны две тонкости. **EXTERNAL** в описании BRAM Controller не означает «внешнюю DDR»: это режим инстанцирования BRAM относительно самого IP. **Single-port BRAM** нельзя интерпретировать как свидетельство уже существующего независимого порта чтения FPGA-логикой.

Устройство видно в `/sys/devices/soc0/amba_pl/40000000.axi_bram_ctrl`, но ссылка на kernel `driver` отсутствует. Наша программа работает **без специализированного драйвера**, через `/dev/mem`, с правами root. Это пригодно для контролируемой лаборатории, но не является рекомендуемой архитектурой окончательного продукта: в дальнейшем предпочтительны собственный драйвер либо UIO, когда это обосновано безопасностью и требованиями ядра.

## 5. Как Linux-программа обращается к аппаратному адресу

На плате выполняется собственная утилита `ebaz20-bram-reader`. Ключевой код исходника:

```c
const int fd = open("/dev/mem", O_RDONLY | O_CLOEXEC | O_SYNC);
void *mapped = mmap(NULL, 8192, PROT_READ, MAP_SHARED,
                    fd, (off_t)0x40000000);
const volatile uint32_t *words =
    (const volatile uint32_t *)mapped;
uint32_t value = words[0];  // 0x00000043 в нашем опыте
```

1. `/dev/mem` предоставляет доступ к физическому адресному пространству при разрешении политики ядра.
2. `mmap()` отображает заданный диапазон физических адресов в виртуальное пространство процесса.
3. `PROT_READ` не запрашивает права на запись в отображённую область.
4. `volatile` заставляет компилятор сохранять обращения к отображённым словам как наблюдаемые операции. **Само по себе `volatile` не обеспечивает всех аппаратных барьеров, атомарности, согласованности кэшей или правильного протокола синхронизации.**
5. В реальной программе проверяются ошибки `open()`, `mmap()` и `munmap()`.

Работа с MMIO зависит также от атрибутов памяти, настроенных ядром для `/dev/mem`, и от требуемых барьеров/упорядочивания. Надёжную многопоточную или DMA-систему нельзя строить, опираясь только на факт успешного простого чтения.

**Ни одна команда в опыте не записывала данные в AXI-окно.** Не следует пробовать `devmem 0x40000000 32 0x...` на текущем заводском bitstream, пока неизвестны назначение данных и реакция существующей PL-логики.

## 6. Воспроизводимый аппаратный результат EBAZ-20

После установки GCC для ARM hard-float в Ubuntu WSL2 мы собрали программу для Cortex-A9 с параметрами:

```text
-mcpu=cortex-a9 -mfpu=neon -mfloat-abi=hard -static
```

`make check` подтвердил **ELF32 ARM, EABI5, hard-float, статическую компоновку**. Программа была доставлена непосредственно в отдельный RAM-backed `tmpfs` на плате. Первоначальная попытка доставки через `/dev` выявила ограничение активного 64-КиБ tmpfs и привела к усечённому ELF; это важный практический результат: **контроль размера и SHA-256 обязателен**.

Аппаратная команда:

```sh
/dev/ebaz20-ram/ebaz20-bram-reader --words 32
```

Контрольные значения:

| Адрес | Значение | Адрес | Значение |
|---|---|---|---|
| `0x40000000` | `0x00000043` | `0x40000020` | `0x0000003F` |
| `0x40000004` | `0x00000001` | `0x40000024` | `0x0000000E` |
| `0x40000008` | `0x00000008` | `0x40000028` | `0x0000001E` |
| `0x4000000C` | `0x00000008` | `0x4000002C` | `0x0000001E` |
| `0x40000010` | `0x00000008` | `0x40000030` | `0x00000000` |
| `0x40000014` | `0x00000008` | `0x40000034` | `0x00000000` |
| `0x40000018` | `0x00000000` | `0x40000038` | `0x00000000` |
| `0x4000001C` | `0x00000000` | `0x4000003C` | `0x00000000` |

Все значения `0x40000040–0x4000007C` равны нулю. Нули сами по себе **не означают свободную память**.

Завершающий вывод:

```text
EBAZ20_BRAM_READ_PASS
EBAZ20_READ32_EXIT=0
```

**Независимый контроль:** значения слов `0x00–0x3C` совпали с предшествующими чтениями через BusyBox `devmem`, а дальнейшее чтение подтвердило доступность ещё 64 байт. Тесты не выявили ошибок шины.

**Статус доказательства:** наша программа выполняет чтение в AXI-адресном окне PL. Роль всех IP-посредников и происхождение значения `0x43` остаются неизвестными. Совпадение `0x43` с ASCII `C` ничего не доказывает о смысле этих данных.

## 7. AXI и производительность: что мы ещё не измеряли

Проверка 32 слов через `mmap()` — это **проверка функциональности**, а не измерение полосы пропускания. На скорость влияют:

- частота интерфейса AXI и частота логики PL;
- число и длина AXI-транзакций, возможность burst;
- задержки interconnect и BRAM Controller;
- мастер PS и топология портов;
- атрибуты отображения памяти, барьеры, кэширование;
- активность других мастеров и конкуренция за шину.

Поскольку наша программа читает 32 слова одним циклом по отображённому адресу, нельзя автоматически считать, что ARM отправил **одну AXI burst-транзакцию**. Такие утверждения требуют трассировки на уровне AXI или инструментального измерения.

## 8. Следующий эксперимент: настоящий двусторонний обмен ARM ↔ FPGA

Нужен **новый, контролируемый RTL-проект**, в котором известно назначение каждого регистра. Возможная карта адресов (только предложение, **не** карта текущего bitstream):

| Смещение от новой базы control | Регистр | Назначение |
|---|---|---|
| `0x00` | `MAGIC` | Узнаваемая константа идентификации |
| `0x04` | `VERSION` | Версия аппаратного протокола |
| `0x08` | `CONTROL` | Команды ARM |
| `0x0C` | `STATUS` | Состояние FPGA |
| `0x10` | `ARG0` | Входной аргумент |
| `0x14` | `RESULT0` | Результат вычисления |
| `0x18` | `SEQ` | Порядковый номер операции |
| `0x1C` | `ACK` | Подтверждение обработки |

Отдельное адресное окно BRAM можно выделить для больших блоков данных, а **AXI4-Lite** использовать для малого управляющего блока. Конкретные адреса должны быть назначены в Vivado, согласованы с PS/PL address map и отражены в Device Tree. Не использовать «для удобства» произвольные адреса старой конфигурации.

### Минимальная проверяемая цепочка будущей лаборатории

```text
ARM: записать ARG0=21, SEQ=1, CONTROL=START
                  |
                  v
 FPGA: принять команду и вычислить RESULT0=42
                  |
                  v
 FPGA: STATUS=DONE, ACK=1
                  |
                  v
 ARM: прочитать STATUS, RESULT0, ACK
       проверить RESULT0=42 и ACK=SEQ
```

Это только **проект тестового протокола**, не выполненный эксперимент. До загрузки собственного bitstream необходимы RTL-тестбенч, проверка тактирования и сброса, карта интерфейсов, тест синтеза, сохранение штатного bitstream и подтверждённая аварийная загрузка. NAND не трогать до завершения приёмки.

## 9. Выводы

**AXI связывает программный и аппаратный миры**: ARM-программа обращается к физическому адресу, а контроллер в PL обрабатывает соответствующую транзакцию. Именно так обычный C-код становится инструментом работы с аппаратным блоком FPGA.

В EBAZ-20 мы получили **аппаратно подтверждённое чтение 128 байт**. Это уже воспроизводимая база для разработки собственного интерфейса ARM ↔ FPGA, но ещё не готовый двусторонний канал обмена.

Следующая исследовательская задача — спроектировать и доказать запись, обработку команды в RTL и обратное чтение результата по контролируемому протоколу.
